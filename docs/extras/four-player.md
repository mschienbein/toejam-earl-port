# Four-player co-op — fail-closed foundation and gameplay design

Status: **tested primitives, not a playable campaign**, 2026-10-25. Main explicitly revised the current implementation to a fail-closed foundation: `tje-four-player` provides typed four-seat sidecar data, level-ID arrival bookkeeping, four-pad routing, runtime palette variants and quadrant layout primitives. Requests to enable four-player reject before mutation until the complete simulation/render closure exists. Two-player faithful play remains the untouched default. New/HD artwork is excluded. The shared cutover, dependencies and staged estimates are in [mode-owned-simulation.md](mode-owned-simulation.md).

`G` is the [matching decompilation](https://github.com/mschienbein/toejam-earl-decomp), researched at commit `57fc83fc54781af8e992bbc3b32afe788c1dbd01`; `G/...` paths are relative to it, and `P/...` paths are relative to this repository. REV 02 addresses come from `G/config/rev02/names.json`.

## Recommended experience

- A separate **Enhanced co-op / 1–4 seats** new-session choice. No hot conversion of an in-progress faithful save; a future explicit import could be designed separately. Original recordings and two-player netplay remain unchanged.
- Default roster: ToeJam, Earl, a runtime recolor of ToeJam, a runtime recolor of Earl. Archetype (animation/stats/dimensions) and seat number are distinct fields; recolors do not silently gain different stats. Each seat can choose either existing archetype.
- Default camera: fixed **2×2 individual views**, each 400×224 world pixels at native density, composed into an 800×448 logical canvas before integer scaling. For two/three seats unused quadrants show a neutral status/map panel, not another simulated player. A 400×224 quadrant is not a 160×112 squeeze of the old framebuffer.
- Optional shared camera is allowed only when all participating heroes are on the same level and fit within a 400×224 safe rectangle with margins. Never zoom so far out that new terrain/enemies are revealed, never teleport or tether a distant hero to keep sharing. Transition to quadrants with fixed hysteresis; layout choice must not change activation, RNG or fog. Default fixed quadrants avoids camera churn and works on separate floors.
- Native local play and browser local play are the initial implementation target. Four-seat peer-to-peer play requires a separate protocol/session extension; the current two-seat Netplay work does not imply support. No hosted matchmaking or TURN service.

ExtendedView coordinated its first envelope as 400×224, or 400×112 for the original two-player horizontal split, adding forty pixels on either side of the original view; above 400 is experimental and initially capped at 512. Its initial implementation does **not** deliver four viewports, a relaxed sprite allocator or changed world dimensions. This feature must explicitly add those capabilities.

## Ownership and EnhancedMode cutover

Use the coordinated non-default `EnhancedProfile(name, &'static [Translation], &'static [FramedTranslation])`. Existing `Context` signatures and physical stack handling are reused. Selected nested calls remain selected; unselected calls execute compiled original code. Atomic/Functional callbacks have a synthetic RTS charge: enhanced gameplay has no cycle-equivalence claim and cannot borrow the faithful source-proof receipts. The existing opt-in `NativeCompiledOriginalCallees` profile ([P `docs/ENGINE.md:437–506`](docs/ENGINE.md#L437)) is the starting dispatch convention, not a second engine or an excuse to edit faithful tables.

**Available foundation:** enhanced typed sidecars/context, four controller states, resumable callbacks and format-3 atomic snapshots now exist; see [ENHANCED_MODE.md](../ENHANCED_MODE.md). **Still missing for playable co-op:** generalized complete world ownership, the phase/setup transaction, enhanced recording/lobby configuration events, frontend seat-binding UI and sidecar-driven host multi-view sprite/HUD composition. The small four-seat data/input/palette primitives do not supply these gameplay services.

Keep the original compiled main-loop entry and device/audio scheduler, but replace the entire selected **world ownership closure**. Each high-level phase adapter reads/writes the sidecar, uses generalized readable algorithms and returns to the original caller. The bridge latches a video-frame ID plus phase and admits each scheduled enhanced phase once; extra renders or repeated entry calls cannot advance it. Retain the original four-phase relative schedule initially. Do not put an endless new loop, blocking map or elevator wait into an Atomic callback.

This table names **ownership roots**, not a complete leaf whitelist. During implementation derive the transitive closure from metadata and all installed callback/data-table targets; reject startup if any sidecar-owned player/map/entity pointer could reach an unmodified RAM-assuming original. Original pure ROM resource reads/math and correctly bounded audio/device routines may remain compiled. No host pointer or seat 2/3 is passed to an original `object_state*` or player-index ABI. An immutable mode manifest records all selected bodies and versions. Do not ship a partial closure that leaves two invisible or invulnerable players.

## Concrete new state

Allocate bounded host memory once per enhanced session, with reusable scratch for hot loops:

- `PlayerId(u8)` 0–3, independent `ArchetypeId` and `PaletteVariantId`; `EntityId(u32)` with generation, `LevelId(u16)` and `ViewId(u8)`. Never reuse signed-char sentinels or raw ROM/function pointers as host object IDs.
- `players[4]`: 24.8 motion, canonical animation state, archetype resources, health/lives/rank/score/bucks, sixteen inventory slots, all fall/jump/skates/sleep/hurt/Hula/remap/respawn timers, active present and effect ownership, 5×5 terrain cache, menu/choice/release latches, elevator reference and optional Jam state. Generalized bounded counters retain intended original wrap semantics where relevant; larger coordinate/distance computations use checked i32/i64 arithmetic.
- `levels`: one entry per visited level (initial campaign 0–26), containing geometry/path edits, reveal/visited bits, anchors/elevators, Earthling/item records and stable collected/removed bitsets. Up to four levels need active simulation; keep lightweight mutable state for all visited levels so splitting and returning cannot regenerate consumed items.
- Persistent Earthlings are distinct from transient draw objects. Use four-seat target/contact masks and separate health/status fields instead of overloading the original two-byte health/visibility array. Starting default remains twenty persistent Earthlings per ordinary level; raising density is a separate optional setting.
- Effects/projectiles/drops use bounded session pools with explicit per-player quotas and atomic allocation transactions. Default proposed capacity: 256 runtime entities, 64 projectiles, 128 drops; reserve required player/elevator/ship resources so cosmetic allocation cannot block progression. Fail a cosmetic spawn without altering simulation; never evict an authoritative actor because a viewport ran out of sprites.
- `phase`, input frame, four pad/action words, independent deterministic RNG streams, shared world seed/ruleset version, config events and ordered mutation queue. Level changes commit before map queries for the new level; same-tick item claims use a rotating seat-priority seed recorded in state, so exactly one inventory receives the item.
- Camera transforms and draw lists are rebuildable presentation state unless they determine discovery/activation; any such dependency must instead live in authoritative interest state and be snapshotted. No per-frame heap allocation or full-world copies; use stable arenas, dirty cells and spatial bins.

Budget [INFERENCE]: four-player state under 16 KiB; twenty 18-byte original-style Earthling records and 32 eight-byte items are only about 616 bytes/level before host IDs/status expansion. Allow 4 MiB total authoritative enhanced state (including 27 visited levels and 256 runtime entities) and 64 MiB derivative graphics/cache storage initially. These are explicit host budgets, not claims of free Genesis RAM. Larger/Maker caps are negotiated separately.

## Four pads, recordings, snapshots and network

- Extend frontend seat assignment to four modern pads/keyboard bindings with stable reconnect identity and explicit seat-enable bits. Never assign by the current order returned by an OS/browser poll. Disconnection produces neutral input for that seat, not automatic ownership transfer; a recorded lobby event reassigns it.
- New `EnhancedInputFrame` contains frame ID, four existing session-format pad words (including connected bit) and four enhanced action words. Existing session wire button order is Up/Down/Left/Right/A/B/C/Start; original game RAM order is directions/B/C/A/Start (G F9). Conversion is explicit and tested.
- Existing faithful `tje-session` has two-pad records ([P `crates/tje-session/src/lib.rs:1–5,80–90,130–141`](crates/tje-session/src/lib.rs#L1)); native controllers also have two seats ([P `crates/tje-native/src/input.rs:245–249,420–423`](crates/tje-native/src/input.rs#L245)). Add a versioned **enhanced** recording schema; do not quietly pad or reinterpret faithful recordings.
- Snapshots peer specifies core format 1 (`TJESTATE`): actual ROM SHA1, frame, 25 canonical CPU words and full retained device/timing/input/audio state, with checksum, but no enhanced identity/sidecar. Wrap it transactionally with profile/body-manifest/ruleset versions, ROM identity, config/course digest, four inputs and complete sidecar state. Reject mismatch before mutating either half. Restore/rebuild caches from the user's ROM. Core state files remain private ROM derivatives.
- Four-seat rollback needs input ownership, prediction/confirmation for all seats, complete sidecar hashes and a negotiated seat map/config manifest. A two-peer lobby can support multiple local seats; three/four independent peers need a separately designed P2P topology and disconnect policy. No assumption that existing two-player Netplay packets can carry it.

## Rendering, characters and balance

Host rendering resolves sprite frame/sequence/metatile resource IDs from the user's ROM at runtime and emits per-view instances using authored priority/flip/Y ordering. Keep a stable tie order by entity ID. Draw at most the selected views, but compute actor activity from a fixed player-centered interest envelope independent of window dimensions. Four overlapping viewports share decoded resources, not hardware sprite slots; GPU capacity cannot choose collision winners.

Palette transforms operate on decoded ROM colors at runtime, preserve transparency/index semantics and retain outline/contrast. Use per-instance palette textures/uniform bindings, plus seat number/icon indicators for color-blind readability; do not reprogram a global CRAM slot for each hero. No extracted palette tables, tiles, frame captures, original text or sound bytes enter P.

Proposed initial balance:

- Archetype stats/speeds unchanged. Cooperative difficulty presets scale **spawn composition/count and resource supply**, not hidden hero damage or HP. Default four-seat resource supply is approximately twice the two-seat item budget, subject to density caps; show the setting in session identity.
- Enemies still prefer decoys, then eligible nearest same-level hero; extend original equal-distance preference to the higher seat ID for deterministic compatibility with the original two candidates. Contact order rotates per encounter tick, with each hero processed at most once.
- One global ship-part collection state, per-seat score/inventory; item claims are atomic. One collected part cannot count twice. Health-sharing requires an explicit nearest eligible donor/recipient pair and conserves transferred health; life donation names its recipient and cannot chain in the same tick.
- Elevator riders are a bitmask/cohort. Heroes may travel separately or fall to different floors; doors close after a visible, fixed join window, then the cohort transition is atomic. Shared-camera play does not force all four to ride. An eliminated hero can request an identified donor or spectate; surviving hero selection is deterministic, not `player ^ 1`.
- Inventory/map are per-seat overlays and do not grant immunity or freeze enemies; input neutralizes that hero's movement while the world continues. A separate cooperative pause requires all local/remote seats' agreed pause state. This deliberately differs from original visibility-dependent menu blocking and must be documented in settings.

## Phases, tests and risks

Estimates are design judgments [INFERENCE], engineering days after the faithful readable layer is usable. Shared foundations are shown once here and are reusable by larger levels, Maker and Overlord.

| Phase | Observable exit | Estimate |
| --- | --- | --- |
| F-A shared | Typed sidecar/context service, phased bridge, enhanced envelope/hash/identity and fail-closed closure manifest; native and wasm | 5–9 days |
| F-B shared | Host entity/metatile/palette pipeline and four-seat input/recording/lobby assignment | 6–10 days |
| F-C | Generalize players, inventories, effects/collision/AI, four level lifetimes, falls/elevators/death/ship progression | 12–20 days |
| F-D | Quadrant/shared-camera UI, four overlays, palette variants and local usability | 5–8 days |
| F-E | Full campaign integration, determinism/resource pressure regression and balance | 6–10 days |
| F-N optional later transport | Extend two-seat rollback/session negotiation to four seats and multi-peer P2P, if requested | 8–15 days beyond local mode |

Required tests:

1. Existing REV 00/REV 02 faithful native/browser session **frame and audio hashes unchanged** with extras absent/off; faithful default config never constructs the enhanced profile. New enhanced runs get their own baselines.
2. Four distinct simultaneous inputs, hotplug/reconnect, swapped A/C, independent menus/map/choices/pause, keyboard focus and multiple local seats per peer. Assert session-pad ↔ original-byte conversion for every bit.
3. Each archetype in each seat through every original ability/status, rank/life edge, falling (including four different floors), split return, telephone, doorway, mole theft, Santa, health sharing, life donation, elevator cohort and final ship progression. All twenty-eight present identities must reach all four seats through real effects, not a narrowed movement demo.
4. Two/four heroes and four decoys at equal distances; contact/latch masks; simultaneous pickup/purchase/part collection; deterministic collision tie order; distance and coordinate bounds.
5. All four heroes occupy different levels, mutate land/collect items, swap levels repeatedly, die and rejoin. State follows LevelId, not camera slot. No duplication or loss after cache eviction/restore.
6. Four views on one dense scene and four disjoint scenes; full inventories/effect pools; forced renderer cache eviction. Simulation must match regardless of view layout, integer scale, frame skipping or GPU residency. No inherited 80-sprite/scanline dropout in host view packets.
7. Native/wasm same manifest + inputs yield identical authoritative hashes and enhanced audio; snapshot/restore/replay across every phase and transition; renderer cache rebuilds are observationally identical.
8. Audit full selected/callback closure before admission, including original data-table callbacks and UI/elevator nonlocal paths. Unsupported original waits cannot be silently ignored; replace blocking sequences with mode state machines before that feature is enabled.

Principal risks: broad two-player assumptions hidden in readable leaves; rendering/animation/physics coupling; transition and interaction latches; a plausible-looking four-character demo that does not survive a campaign; small-screen readability. Fixed quadrants and typed state are recommended defaults, not user decisions that block these documents. Whether to fund four-independent-peer play, new artwork, or change the default camera later remains a user choice; no such work is implicitly approved here.

Main owns final integration gates. The current foundation has no admitted four-player profile, frontend session choice, simulated present/AI/transition closure, host four-view compositor or four-pad gameplay recording. Codec/arrival-bookkeeping/rewind tests and private runtime palette previews are not evidence of a playable co-op session. The gameplay acceptance above remains the gate for the later shared cutover; current primitive coverage and exercised checks are reported separately.
